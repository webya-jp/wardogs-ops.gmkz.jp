## 他の重点項目の結果

### 2 PBKDF2(`src/lib/password.ts`)

- salt は 16 バイトの `crypto.getRandomValues`(登録・再ハッシュのたびに新規)。導出値 32 バイト。保存形式 `pbkdf2-sha256$<回数>$<salt>$<導出値>`。パース時に回数 1,000〜100,000・salt 16 バイト・導出値 32 バイトを検証し、外れたものは `invalidHash`(コードだけをログへ)。
- 比較は導出値 32 バイト同士を `timingSafeEqualBytes`(Workers の `crypto.subtle.timingSafeEqual`、無ければ XOR 累積)。
- 反復回数 1 万回の根拠は ARCHITECTURE 5.2 の実測表(workerd で約 4.4 ms)と、ログインの CPU 10 ms 上限(Error 1102 を避ける)。D1 を読める相手は `instance_key` も読める、という整理も含めて妥当。本番実測は C-C。
- 再ハッシュ(`admins.ts:84〜90`)は `WHERE id = ?3 AND password_hash = ?4` で旧値を照合し、`session_stamp` は変えない(ログイン中の人を追い出さない)。並行ログインでも二重に上書きしない。
- ハッシュ・平文は応答に出ない(`AdminRow` は `admins.ts` と `auth.ts` の中だけで使われ、API 応答の型に含まれない)。

### 3 鍵派生(`src/lib/keys.ts`)

- `instance_key`: `randomB64url(32)`(`getRandomValues`)。`SELECT` → 無ければ `INSERT OR IGNORE` → もう一度 `SELECT`(`keys.ts:56〜70`)。並行しても最初の 1 行だけが使われ、形式不正は例外(鍵を作り直さない)。
- キャッシュは isolate 内 5 分。D1 の失敗はキャッシュしない(`keys.ts:89`)。鍵・`instance_key` を返す・ログに出す経路は無い(`DerivedKeys` は `CryptoKey` のみ)。
- 5 分キャッシュのため、`instance_key` を手で消した直後は isolate ごとに新旧の鍵が混在し得る(ARCHITECTURE 5.1.2 で受け入れ済み)。

### 4 Cookie v2(`src/lib/session.ts`)

- 署名対象は `v2.<aid>.<sid>.<iat>.<exp>.<op>.` + その管理者の `session_stamp`(`signingInput`)。HMAC-SHA256 は session 鍵。形式・長さ(512 文字上限)を確かめてから `admins` を主キーで読み(キャッシュなし)、`timingSafeEqualBytes` で比較。`admins` の行が消える・`session_stamp` が変わる・`id` が変わる(AUTOINCREMENT)と通らない。`exp - iat !== SESSION_TTL_MS`・期限切れ・未来の `iat`(5 分超)を拒否。`op` は base64url の UTF-8 を復号して再整形。
- 属性: 本番 `__Host-wo_session`、`Path=/; HttpOnly; SameSite=Strict; Max-Age=43200; Secure`、Domain なし。開発のみ `wo_session` で `Secure` なし。
- 実機確認: 不正な v2 Cookie と v1 Cookie は、API は 401、ページは 303 `/login`。
- 補足(設計どおり): 署名 Cookie は状態を持たないため、ログアウト(`/logout`)では `session_stamp` を変えない。ログアウト前に盗まれた Cookie は期限(12 時間)まで有効。README に明記済み(0 章、6.3)。

### 7 画面(`/setup`、`/login`、375px)

- `/setup`(`setup.astro`): `autocomplete="new-password"`(2 欄とも)、`minlength` / `maxlength`、再表示なし(`value` 属性を出していない。エラー時の再表示でも空)、文言はすべてカタログ経由。JS は補助のみ(確認入力の不一致の検知、送信中のボタン無効化、bfcache 復帰時の解除)。JS が無くても Worker が同じ検証をし、2 回目は 409。サーバー側の原子性があるので二重送信による二重登録は起きない。
- 状態ごとの出し分け: D1 の不備(フォームなし・POST は 503)、未登録(フォーム)、登録済み(GET は 303、POST は 409 とログインへのリンク)。実機で 303 / 409 を確認。
