## 提案

### 認証・セッション
- **S-1 SESSION_SECRET を実質必須にするか、自動生成する**。`ADMIN_PASSWORD` が未導出のままだと Cookie と確認トークンの署名鍵はパスワードだけから決まる(`src/lib/keys.ts:28-37`)。Cookie 1 本を入手した者が、オフラインでパスワードを総当たりできる(HKDF は低速化しない)。16 文字の長さ要件は強度を保証しない(辞書的な 16 文字でも通る)。README `:116` は「安全性が少し上がります」と軽く書いているが、実際は構造的な弱点の解消なので、推奨度を上げる(Deploy ボタンのフォームに出す、または未設定時に `/setup` の警告に出す)。設計判断なので二次レビュー対象。
- **S-2 ADMIN_PASSWORD が 256 文字を超えるとログインできない**。`src/lib/password.ts:17` は入力を 256 文字で切り、`src/lib/config.ts:76-79` は上限を検査しない。上限(例 128)を `ADMIN_PASSWORD_TOO_LONG` として警告にする。
- **S-3 確認トークンにセッション ID の全文が入る**(`src/lib/confirm.ts:58`)。中身が JS から読める。Cookie 自体に sid が平文で入っているので新たな漏れではないが、`sid` の SHA-256 先頭の値に替えると、トークンから sid が分からなくなる。
- **S-4 CSRF 修正(57757c4)の評価: 妥当**。`src/lib/csrf.ts:194-206`: Origin が自オリジンと完全一致なら許可。`null` または無しのときだけ `Sec-Fetch-Site: same-origin` を要求し、どちらも無ければ拒否(fail closed)。`Sec-Fetch-Site` は禁止ヘッダでページのスクリプトから偽装できず、`same-site`(兄弟サブドメイン)や `cross-site` は拒否される。`SameSite=Strict` は兄弟サブドメインからのリクエストを止めないので、Origin 完全一致が実質の防御である点も正しく保たれている。実測(dev): Origin 無し / 他サイト / `null`+`cross-site` / `null`+`same-site` はすべて 403。古いブラウザ(`Sec-Fetch-Site` 非対応)は、`Referrer-Policy: same-origin` により同一オリジンのフォーム送信でも Origin が付くので通る。`Origin: null` かつ `Sec-Fetch-Site` 無しの組み合わせだけが拒否で、そのブラウザは Origin 付きのため実害は出にくい。README に「ごく古いブラウザではログインできないことがある」程度を足すかは任意。`OpsLayout.astro:53` の `<meta name="referrer">` はヘッダと重複(無害)。
- **S-5 セキュリティヘッダ**: `Strict-Transport-Security` が無い(workers.dev は HSTS プリロード済みだが、カスタムドメインは無い)。CSP に `script-src` / `default-src` が無い(設計 C-15 の要確認のまま)。React は文字列をエスケープしており、現状 XSS の経路は確認できなかったが、Astro のアイランドが使うインラインスクリプトのハッシュ指定(または nonce)で絞る検討を残す。
- **S-6 ログアウトは Cookie を消すだけ**で、盗まれた Cookie は 12 時間有効(設計 5.4 どおり)。README の注意書きに「共有 PC ではログアウトに加えてパスワードを変える」を足すと誤解がない。
- 確認済みで問題なし: Cookie 属性(`__Host-wo_session`、`Secure; HttpOnly; SameSite=Strict; Path=/`、Domain なし。dev のみ別名・Secure なし、`src/lib/session.ts:146-150`)、HMAC 比較は定数時間(`keys.ts:113-120`)、パスワード比較は HMAC 同士(長さが隠れる)、HKDF の用途別派生、12 時間の絶対期限と `exp-iat` の固定検査(`session.ts:128`)、全パス検証(`/api`、`/api/x/`、パーセントエンコード、`//api`、大文字 `/API` を実測してすべて 401 または `/login` へ 303)、例外は `/login`・`/setup` と静的のみ(M-4 を除く)。

### 書き込み・監査
- **S-7 RCON_TIMEOUT は監査ログ上「失敗」と記録される**(`src/lib/actions.ts:160-165`、`src/components/AuditLog.tsx:410-416`)。実行されたかどうか不明なのに赤い「失敗」バッジになる。`error_code=RCON_TIMEOUT` のとき、画面で「結果不明」バッジにするか、`status` に `unknown` を足す。
- **S-8 書き込み系の 404 を `RCON_ROUTE_NOT_FOUND` に決め打ちしている**(`src/lib/rcon/client.ts:134`、`src/lib/actions.ts:44`)。対象プレイヤーが既に退出していて RCON が 404 を返す実装の場合、「ルートが無い」と誤表示し、capabilities のキャッシュも捨てる。エラー本文の形式が未検証(R-14)なので、実機確認後に 404 の本文で分ける。
- 確認済みで問題なし: 確認トークンの署名(HMAC-SHA256、定数時間比較)、期限(120 秒)、セッション一致、action + params のハッシュ一致、nonce の UNIQUE による 1 回限り(`audit.ts:29-52` の `ON CONFLICT DO NOTHING RETURNING` は原子的)、検証順序が `docs/API.md` 4 章と一致、pending の INSERT が失敗したら RCON を呼ばない(`actions.ts:141-144`)、RCON は 1 回だけ呼び再試行なし、`AUDIT_REQUIRED` が効く(`config.ts:154-162`、`features.writes`)、書き込みは POST / DELETE の API のみ。GET の副作用は S-9 の 1 点のみ。
- **S-9 `GET /api/status` が D1 に書く**(`src/lib/snapshots.ts:15-26`)。`INSERT OR IGNORE` で 5 分に 1 行、冪等で設計 4.4 に記載済み。「GET に副作用を起こさない」の厳密な基準には当たるが、クロスサイトからは Cookie が付かないため悪用できない。許容するなら設計書に「許容する副作用」と明記する。

### RCON 呼び出し
- 確認済みで問題なし: Bearer は `Authorization` のみ、URL・パスワードはログ・エラー応答・クライアントに出ない(例外の文字列は使わず名前だけ)、タイムアウト(読み取り 5 秒 / 書き込み 8 秒、本文読み取り中も有効)、`redirect: 'manual'` で 3xx は `RCON_BAD_RESPONSE`、応答 512 KiB 上限、IP 直指定の拒否(`config.ts:50-51`。WHATWG の正規化後に判定するので 16 進・10 進表記も拒否。IPv6 も拒否)、認証情報つき URL の拒否、capabilities が取れない場合は `unavailable` で 200(10 分 / 失敗時 1 分キャッシュ、refresh は 1 分に 1 回)、`unknown` は有効のまま「未確認」表示。
