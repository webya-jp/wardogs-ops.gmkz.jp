## 提案

### P-1 JS が読み込めなかったときモバイルでサイドバーが閉じたまま開けない

- `OpsLayout.astro`: `<head>` のインライン script が `js` クラスを付けるので、CSS は 1024px 未満で閉じた状態にする(`.js .sidebar:not(.is-open) .sidebar-section { display: none }`)。一方、開閉ボタンを出すのは本文末尾の `<script>`(Astro のモジュール script)だけ。**そのモジュールが読み込めない・実行時エラーになると、閉じた状態のまま開閉ボタンも無く**、スマートフォンでサーバー切り替え・ログアウトに届かない(タブと要約行は見える)。
- 通常の「JS 無効」では `js` クラスが付かないので問題ない(確認済み: ボタンは `hidden`、サイドバーは開いたまま)。回避は、`js` クラスの付与を本文末尾のモジュール script の中で行う(ボタンの `hidden` を外す処理と同時に)こと。

### P-2 見出しの順序: サイドバーの h2 が main の h1 より先に出る

- DOM の順序は スキップリンク → ヘッダー → サイドバー(`h2`「選択中のサーバー」「試合」)→ タブ → main(`h1`)。支援技術の見出し一覧では h2 が h1 の前に並ぶ。設計 9.2 の順序どおりだが、サイドバーの見出しは `aria-label` つきのセクションにして `h2` をやめる、または見た目だけの要素にすると一覧が整う。`SidebarStatus.tsx`(`#sidebar-card-title`、`#sidebar-match-title`)と `Sidebar.astro`(`#sidebar-card-title`)。

### P-3 開閉ボタンの名前を状態で変えない方がよい

- `OpsLayout.astro`: ラベルが「サーバーの情報を開く」と「閉じる」に変わり、同時に `aria-expanded` も変わる。支援技術では「閉じる、折りたたみ済み」のように二重に伝わりやすい。名前は固定にして `aria-expanded` だけで状態を伝えるのが定石。見た目の「開く / 閉じる」は別の span にして `aria-hidden` にする手もある。

### P-4 `/api/status` の直列取得による最悪の待ち時間

- `src/lib/reads.ts` の `readStatus`: `/v1/status`(最大 5 秒)→ `getCapabilities`(キャッシュが切れていれば最大 5 秒)→ `/v1/rotation`(最大 3 秒)の順に直列。キャッシュが温まっていれば追加は 0〜1 回だが、10 分ごとの capabilities 更新と 5 分ごとの rotation 更新の直後は 1 回の `/api/status` が最悪 13 秒近くになり得る。サブリクエストは最大 3 + D1 で上限内。`getCapabilities` と `/v1/status` を並行にすると最悪 8 秒に縮む。動作は壊れない。

### P-5 `/v1/rotation` のキャッシュ破棄は同じ isolate 内だけ、取得中の相乗りは破棄の対象外

- `src/lib/reads.ts` の `invalidateRotation` は呼んだ isolate のキャッシュだけを消す。別の isolate は最大 300 秒、`map` / `match_end` の前のローテーションを返し続ける。ただし `nextIndex` は毎回 `/v1/status` の値で、並び自体は変わらないため実害は小さい。API.md 3 章に「同じ isolate 内のみ」と一言足すとよい。
- `rotationInflight`: 取得中に `invalidateRotation` が呼ばれても、取得中の結果が後からキャッシュに書き戻される。窓は 3 秒以内。
- `src/lib/actions.ts`: `map` / `match_end` が `RCON_TIMEOUT`(結果不明)のときは破棄しない。上と同じ理由で実害は小さい。

### P-6 ポーラー: 非表示のタブで開いたとき初回の 1 回は取得する

- `src/components/lib/poller.ts` の `start()` は `document.visibilityState` を見ずに `load()` を呼ぶ。バックグラウンドタブで開いた場合、1 回だけ取得してから止まる。設計の「タブ非表示で停止」とは僅かにずれるが、表示に戻ったときにすぐ最新が見えるので妥当。気にするなら hidden のときは `onVisibility` 待ちにする。

### P-7 型の `?` が残っている

- `src/types/api.ts` の `StatusResponse.experiences?`、`StatusRotation.count?` / `nextMap?` / `nextMapName?`: backend の実装(c6f2ee0)は済んでいて、`normalizeStatus` は常に 4 項目を返す。コメントの「backend の実装後に `?` を外す」が残っている(architect)。`API.md` 3 章の「3 項目は省略され得る(型は `?`)」も同時に直す。画面側は `?? []` / `?? null` で守っているため動作に影響なし。

### P-8 `BansTable.tsx` の無駄な再取得とインデント

- `onDone` が `refreshSharedStatus(server.id)` を呼ぶが、BAN の解除は `/api/status` の内容を変えない。サイドバーの購読者がいれば RCON への余計な 1 回になるだけで害は小さいが不要。`onDone` の括弧とインデントも他と揃っていない。

### P-9 `killfeed.why` の断定

- `src/i18n/ja.ts` の `killfeed.why`: 「RCON にはキルや接続の出来事を取り出す仕組みが無い」と断定している。設計 9.6 の根拠は「HTTP API に該当ルートが資料上見当たらない」(未検証)まで。「現在確認できている RCON の API には見当たりません」のように弱めると、`CLAUDE.md` の「推測で断定しない」に沿う。

### P-10 サイドバーの静的な状態表示に長い文を使っている

- `Sidebar.astro`: 使えないサーバーで原因が「無効」「パスワード再入力」以外のとき、状態の印に `server.unusable.other`(「このサーバーは現在使えません。『設定』を確認してください。」)という文全体を出す。短い印(`sidebar.state.error` 等)のほうが他の状態と並びが揃う。実害なし。

## 確認した内容(問題なし)

### レイアウト(重点 1)

- 設計 9.2 との一致: HTML の順序(スキップリンク → ヘッダー → サイドバー → タブ → お知らせ → main)、見た目は `grid-template-areas`、1024px 以上は 288px + `minmax(0, 1fr)` と sticky の `100dvh` サイドバー、縦ナビは `nav.ts` の同じ配列から作成(キルフィードは `inSidebar: false`)、最下部の操作者・期限・ログアウト(`margin-top: auto`)、すべて設計どおり。
- JS 無し: 開閉ボタンは `hidden`(`[hidden] { display: none !important }`)で、`js` クラスが付かなければサイドバーは常に開いた状態。セレクトは GET フォーム + 常に表示の「切り替え」ボタンで送れる(JS があれば選択で即送信)。要約行は `display: none` で、閉じた状態のときだけ出る。
- `aria-expanded` / `aria-controls="sidebar"`(`id="sidebar"` あり)、`aria-current="page"`(タブと縦ナビの両方)、2 つの `nav` に別名(`tabs.label` / `sidebar.nav`)、`aside` に `aria-label`、ARIA の tablist を使わない判断(設計 9.2 に理由あり)。開閉ボタンとタブのタップ領域は 44px 以上。
- 375px(CSS を読んだ判断。実測は未実施): 1 カラムの `minmax(0, 1fr)`、タブ列だけ `overflow-x: auto`(`flex: none` の `li`、`white-space: nowrap`)、`.sidebar-kv` は `max-content minmax(0, 1fr)` で `dd` に `overflow-wrap: anywhere`、ホスト名は `word-break: break-all`、セレクトは `flex: 1 1 0; min-width: 0`。`body { overflow-x: hidden }` は外されており、はみ出しを隠す指定は無い。はみ出し得る要素を作る CSS は見つからなかった。
- 未認証経路(dev サーバー 4322 に `curl`): `/`、`/players`、`/servers`、`/killfeed` は 303 → `/login`、`/api/status` は 401、すべて `cache-control: no-store`。新ページ `/killfeed` も `PUBLIC_PATHS`(`/login`、`/setup`)に含まれず認証を通る。

### 共有ストア(重点 2)

- 二重取得なし: `getStatusStore` は `globalThis` のレジストリでサーバー id ごとに 1 つ。サイドバーとメインは同じポーラーを購読し、`load()` は取得中なら何もしない(相乗り)。`useResource` は他の API 用に別ポーラー。
- 参照カウント: 購読者 0 で `visibilitychange` の解除・タイマー停止・取得の abort。`subscribe` の戻り値は二重呼び出しでも安全。レジストリはサーバー数(最大 20)で頭打ち。
- 非表示で停止(`schedule` が hidden なら張らない、`onVisibility` で再開)、間隔は `Math.max(pollSec, POLL_MIN_INTERVAL_SEC)`。`UNAUTHENTICATED` で以後の自動更新を止める。
- サーバー切り替え: 通常のページ遷移(全再読み込み)で、ストアは id ごと。前のサーバーの状態は引き継がれない(`ClientRouter` / View Transitions は未使用)。
- SSR: `registry()` は `window` が無ければ `null` を返し、SSR では毎回新しいポーラー(購読もタイマーも無し)になる。Worker の isolate にリクエストをまたぐ状態は残らない。`getServerSnapshot` は固定の `INITIAL_SNAPSHOT` で hydration の不一致なし。
